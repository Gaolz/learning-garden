Blog Post Structure

Quick-reference card for writing technical blog posts in English.

The Skeleton

Every technical blog post follows this structure:

  1. Hook (1-2 sentences) — the problem or promise that grabs the reader
  2. Context (1 short paragraph) — why this matters now
  3. Solution (the body) — steps, code, explanations broken into Claim→Evidence→Implication paragraphs
  4. Conclusion (2-3 sentences) — what you learned, what the reader should do next

Title Patterns

PatternExample
How to X"How to Set Up Hot Reload for a Go + Docker Dev Environment"

Voice: What "Conversational" Means

Avoid (academic)Prefer (conversational)
"One might consider implementing...""You could implement this by..."
"It is noteworthy that..."(Just state the thing. Skip this phrase.)
"In conclusion, it can be stated that...""The takeaway:" or "Bottom line:"
"The aforementioned approach...""This approach..."
Do not use contractions.Use contractions (don't, it's, you're). They sound human.

Code Blocks: The Pattern

Every code block gets three things:

  1. Before — one sentence setting up what the code does
  2. The code — self-contained, runnable if possible
  3. After — one sentence pointing out what to notice

Tense & Voice Quick Reference

SectionTenseExample
Context/BackgroundPresent or Past"We currently run three separate caches."
Proposed Solution / Tutorial StepsFuture/Imperative"We will add a Redis layer." / "Install the package:"
Trade-offs / ExplanationPresent"This introduces a new dependency."
Takeaway / ConclusionPresent or Imperative"Start small. Ship early. Measure."

Common Mistakes (Non-Native Writers)

  • No TL;DR. Busy readers scan the title and first paragraph to decide if they'll read. Lead with the point.
  • Overusing passive voice. "It was decided" hides who decided. Say "we decided" or "I chose."
  • Too many ideas. One post = one main idea. Scope is your friend.
  • Explaining code twice. Good code + one clear sentence of explanation. Not two paragraphs.
