Lesson 1: The Technical Paragraph

The atomic unit of all technical writing. Master this, and blog posts, documentation, and design docs all become easier.

Why This Matters

Most developers who learn English as a second language think they need perfect grammar before they can write. They don't. What they need is structure. A well-structured paragraph with imperfect grammar communicates more than a grammatically perfect paragraph with no structure.

Every piece of technical writing — a blog post, a README, a design doc — is built from paragraphs. If you can write one clear technical paragraph, you can write ten. If you can write ten, you can write a post.

The Pattern: Claim → Evidence → Implication

Good technical paragraphs follow a three-part structure:

  1. Claim — state your point directly. No warm-up.
  2. Evidence — back it with a concrete example, data point, or code snippet.
  3. Implication — tell the reader why they should care.

Here is the pattern in action:

Claim: Caching at the edge dramatically reduces latency for global users.

Evidence: When we moved our static assets from a single-region origin server to a CDN with 200+ edge locations, P95 latency for users in Asia dropped from 2.1s to 340ms.

Implication: If your user base is geographically distributed, a CDN is not optional — single-region serving will cost you real users.

Key insight Notice the paragraph starts with the point, not the setup. Many non-native writers feel they need to "warm up" with background. In technical English, lead with the claim. The reader is busy and will decide in the first sentence whether to keep reading.

What "Concrete" Means

The Evidence step is where non-native writers most often go wrong. Instead of a concrete example, they write another abstract sentence. Compare:

Vague (weak)Concrete (strong)
"This approach improves performance significantly." "This approach cut page load time from 4.2s to 1.1s."
"Many developers find this tool useful." "The tool has 12,000 GitHub stars and is used by teams at Stripe and Shopify."
"The old implementation had problems with scale." "The old implementation crashed at 500 concurrent connections."

Ask yourself: could another writer write the same sentence about a completely different thing? If yes, it's too vague. Add numbers, names, or specific outcomes.

Practice: Write Your Own

Your turn. Pick a technical concept you know well — a tool, a pattern, a bug you fixed, a library you use. Write one paragraph following Claim → Evidence → Implication.

Write it in a text file, a note, or directly in your terminal. Then come back and check it against the guidelines below.

If you want feedback, paste it into this conversation and the agent will review it.

Self-Check Guidelines

  1. Does the first sentence state the point directly — no warm-up?
  2. Does the second part include something specific (a number, a name, a before/after)?
  3. Does the last line answer "so what?" — why the reader should care?
  4. If you remove the Evidence sentence, does the paragraph lose its power? (It should.)
