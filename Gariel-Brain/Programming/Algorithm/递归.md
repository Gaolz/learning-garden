# 每日算法：递归 (Recursion)

> **一句话总结：** 函数自己调用自己，把大问题不断拆成相同结构的小问题，直到小到可以直接解决。

---

### 1. 🎯 解决的核心问题

- **现实痛点：** 面对嵌套结构（树、目录、括号匹配）或具有自相似性质的问题时，用循环需要手动维护栈、写一堆 while/for 嵌套，代码又臭又长；而递归让你用"同一套逻辑处理同一类结构"，天然匹配问题的形状。

- **应用场景：**
  - 树/图的遍历（DOM 树、文件系统、抽象语法树）
  - 分治算法（归并排序、快速排序、二分查找）
  - 回溯问题（N 皇后、数独、全排列、组合）
  - 编译器前端（递归下降解析器）
  - 动态规划（记忆化递归是 DP 的直觉入口）

---

### 2. 📊 复杂度与优缺点

| 维度 | 指标 / 特性 | 补充说明 |
| :--- | :--- | :--- |
| **时间复杂度** | 因问题而异 | 每个子问题被递归调用决定的运算次数 |
| **空间复杂度** | 递归深度 × 每层开销 | 调用栈帧本身占内存，深度过大可能爆栈 |
| **是否尾递归优化** | Ruby 不支持 TCO（默认），Rust 支持（需 `become` 关键字或手动改写为循环） | 尾递归可将空间从 O(n) 压到 O(1) |

- **优点：**
  - 代码简洁、结构清晰，一次写对之后"声明式"地表达了算法
  - 天然适合处理嵌套/递归定义的数据结构（树、图、JSON）
  - 记忆化（memoization）加成后，可以直接变成 DP 解法
- **缺点：**
  - 栈溢出风险：深度过大（如 10^5 层）会 Stack Overflow
  - 重复计算：无缓存的朴素递归（如斐波那契）指数级爆炸
  - 调用开销：每次递归都有函数调用帧的压栈/弹栈成本

---

### 3. 🎨 算法示意图 (Diagram)

以 **归并排序 (Merge Sort)** 为例展示递归的分治过程：

```
                    [38, 27, 43, 3, 9, 82, 10]
                              │
              ┌───────────────┴───────────────┐
              │                               │
        [38, 27, 43, 3]                 [9, 82, 10]
              │                               │
        ┌─────┴─────┐                   ┌─────┴─────┐
        │           │                   │           │
     [38, 27]    [43, 3]            [9, 82]      [10]
        │           │                   │           │
     ┌──┴──┐    ┌──┴──┐            ┌──┴──┐        │
     │     │    │     │            │     │        │
   [38]  [27] [43]  [3]          [9]  [82]     [10]    ← 触底（base case）
     │     │    │     │            │     │        │
     └──┬──┘    └──┬──┘            └──┬──┘        │
        │           │                 │           │
     [27,38]    [3,43]            [9,82]       [10]     ← 回溯合并
        │           │                 │           │
        └─────┬─────┘                 └─────┬─────┘
              │                             │
        [3,27,38,43]                 [9,10,82]         ← 再合并
              │                             │
              └──────────────┬──────────────┘
                             │
                   [3,9,10,27,38,43,82]               ← 最终有序
```

**逻辑推演步骤：**

1. **Step 1 (Base Case)：** 数组长度 ≤ 1，直接返回——已天然有序。
2. **Step 2 (Divide)：** 向下取半，拆成左右两个子数组，分别递归调用。
3. **Step 3 (Conquer & Merge)：** 左右递归返回后，用双指针将两个有序子数组合并为一个有序数组。

### 4. 💻 代码实现 (Ruby & Rust)

#### 💎 Ruby 实现（注重表达力与优雅）

```ruby
# Merge Sort — 递归分治
def merge_sort(arr)
  # Base case: 长度为 0 或 1，已经有序
  return arr if arr.size <= 1

  # Divide: 拆成两半
  mid = arr.size / 2
  left  = merge_sort(arr[0...mid])
  right = merge_sort(arr[mid..])

  # Conquer: 双指针合并
  merge(left, right)
end

def merge(left, right)
  result = []
  i = j = 0

  # 双指针遍历，谁小放谁
  while i < left.size && j < right.size
    if left[i] <= right[j]
      result << left[i]
      i += 1
    else
      result << right[j]
      j += 1
    end
  end

  # 收尾：把剩余的直接拼上
  result.concat(left[i..]).concat(right[j..])
end

# --- 另一个经典递归：斐波那契 + 记忆化 ---
def fib(n, memo = {})
  return n if n <= 1          # base case
  memo[n] ||= fib(n - 1, memo) + fib(n - 2, memo)
end

puts merge_sort([38, 27, 43, 3, 9, 82, 10]).inspect
# => [3, 9, 10, 27, 38, 43, 82]
puts fib(50)  # => 12586269025（有 memo 瞬间出结果）
```

#### 🦀 Rust 实现（注重所有权、类型安全与内存效率）

```rust
/// Merge Sort — 泛型递归实现
/// T: Ord（可比较）+ Clone（需要复制元素）
pub fn merge_sort<T: Ord + Clone>(arr: &[T]) -> Vec<T> {
    // Base case: 切片长度 ≤ 1，直接转成 Vec 返回
    if arr.len() <= 1 {
        return arr.to_vec();
    }

    // Divide: 拆成左右两半
    let mid = arr.len() / 2;
    let left  = merge_sort(&arr[..mid]);
    let right = merge_sort(&arr[mid..]);

    // Conquer: 合并
    merge(&left, &right)
}

fn merge<T: Ord + Clone>(left: &[T], right: &[T]) -> Vec<T> {
    let mut result = Vec::with_capacity(left.len() + right.len());
    let (mut i, mut j) = (0, 0);

    while i < left.len() && j < right.len() {
        if left[i] <= right[j] {
            result.push(left[i].clone());
            i += 1;
        } else {
            result.push(right[j].clone());
            j += 1;
        }
    }

    // 收尾
    result.extend_from_slice(&left[i..]);
    result.extend_from_slice(&right[j..]);
    result
}

// --- 斐波那契 + 记忆化（HashMap 做缓存） ---
use std::collections::HashMap;

pub fn fib(n: u64, memo: &mut HashMap<u64, u64>) -> u64 {
    if n <= 1 {
        return n;
    }
    if let Some(&val) = memo.get(&n) {
        return val;
    }
    let val = fib(n - 1, memo) + fib(n - 2, memo);
    memo.insert(n, val);
    val
}

fn main() {
    let arr = vec![38, 27, 43, 3, 9, 82, 10];
    println!("{:?}", merge_sort(&arr));
    // => [3, 9, 10, 27, 38, 43, 82]

    let mut memo = HashMap::new();
    println!("{}", fib(50, &mut memo)); // => 12586269025
}
```

### 5. 💡 Ruby vs Rust 编程体会

**Ruby 视角的思考：**
Ruby 把递归写成"一行流"是天生的——`return arr if arr.size <= 1` 这种 guard clause + 数组切片 `arr[0...mid]` 让分治思路一目了然。`memo[n] ||=` 完美表达"有就用，没有就算"，一个操作符包含检查和赋值两步。Ruby 不需要操心类型约束、生命周期，只管表达算法骨相——非常适合做原型验证和算法面试白板思维训练。

**Rust 视角的思考：**
Rust 让"成本"无处隐藏：`.clone()` 显式标注了每次堆分配的代价，`&[T]` vs `Vec<T>` 强迫你区分借用的视图和拥有所有权的结果。这不是啰嗦，而是**精确性**——编译期就知道哪一步会分配内存。泛型约束 `T: Ord + Clone` 是算法能力的类型声明："我能排序任何可比较、可克隆的类型"。`Vec::with_capacity` 预分配避免多次扩容，性能细节全暴露。Rust 写递归更像在用类型系统做 correctness proof，一旦编译通过，内存安全已是 guarantee。

**思维的碰撞：**
Ruby 说"你想干什么，写出来就行"；Rust 说"你想干什么，先说清楚你能对数据做什么"。前者加速思考，后者加深理解。两个都写一遍，才算真正懂了递归。
